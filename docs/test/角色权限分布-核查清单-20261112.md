# 班务星角色权限分布核查清单（上线前）

- 核查日期：2026-11-12
- 核查范围：`back/src` 全部业务模块 + `front/src` 角色相关入口
- 核查方式：逐个控制器/服务读取鉴权分支（全局守卫、装饰器、服务层判定、字段过滤）

## 一、角色模型

| 层级 | 角色 | 产生方式 | 说明 |
|---|---|---|---|
| 平台层 | 监控台管理员 | 环境变量 `MONITOR_ADMIN_PHONES` 手机号白名单 | 系统没有「平台超级管理员」角色字段，白名单是唯一平台级身份 |
| 组织层 | owner（群主/创建者） | 创建组织自动获得；可转让 | 每班唯一，不可退出、不可被移除 |
| 组织层 | admin（管理员） | 仅 owner 可设置 | 设置时自动 `is_committee = true` |
| 组织层 | member（普通成员） | 邀请码/二维码加入、名单导入 | 默认身份 |
| 展示字段 | role 字符串（学生/班长等） | 创建、导入、手动设置 | **仅用于展示，不参与任何鉴权** |
| 未落地 | `class_roles.permissions` | 表结构存在 | 全库无读取逻辑，自定义角色权限未实现 |

关键机制：

- JWT 只携带 `userId`，不含角色；每次请求查库取身份（`back/src/modules/auth/strategies/jwt.strategy.ts:20-27`）。
- `ClassIsolationGuard` 只从 `params.classId`、`params.id`、`query.classId` 取班级 ID，校验成员归属后注入 `roleLevel`（`back/src/common/guards/class-isolation.guard.ts:35-62`）。**classId 放在 body、或参数名不是 id/classId 的接口不会被它校验。**
- 全局守卫顺序：Throttler → JwtAuth → ClassIsolation → RoleLevel → Csrf（`back/src/app.module.ts:81-100`）。
- `is_committee` 在现有代码中只在「创建者」和「设为管理员」两处置 true，实际等价于 owner/admin；但没有数据库约束保证两者一致。

## 六、上线前必须处理（P0：越权/数据泄露）

1. **任意成员可发布全班通知**：后端无角色校验，前端全员显示发布按钮 → 任何学生可发署名通知并设置签收截止。`messages.controller.ts:29-37`、`messages.service.ts:20-68`。
2. **任意成员可执行 Excel 名单导入并批量踢人**：`import-student-excel` 只校验「是成员」，传 `sync=true` 会删除名单外的所有成员（群主除外）。`class-import.controller.ts:74-81`、`classes.service.ts:1104-1109,1244-1257`。
3. **资料库上传/下载无班级归属校验**：任意登录用户可向任意 classId 上传；凭 fileId 可读取/下载其他班级文件。`material.controller.ts:31-53,82-95`、`material.service.ts:20-40,538-604`。
4. **班级档案跨班 IDOR**：`archiveId` 不属于 URL 中的班级也能读取、下载附件、导出整包。`archive.controller.ts:20-76`、`archive.service.ts:42-49,79-131`。
5. **专注记录可越权查看**：`GET sessions?userId=他人` 返回他人专注记录（含任务标题、时长）；`GET sessions/:id` 不校验归属。`pomodoro.service.ts:94-134`。
6. **错误监控面任意登录用户可读写**：可读全量错误堆栈、IP、设备、用户 ID，可改状态、增删改解决方案。`errors.controller.ts:56-94,133-171`。
7. **考勤报表无权限判定**：`getReport` 不校验角色与班级归属。`attendances.service.ts:617-709`。
8. **作业离线核对结果任意班员可读**：拿到 checkId 即可读取全班已交/未交名单+学号+姓名。`homeworks.service.ts:571-649`。
9. **生产环境必须配置 `MONITOR_ADMIN_PHONES`**：未配置时监控台与反馈管理在生产会全部拒绝（可用），但一旦误部署到非生产配置为空，任何登录用户都能看全量用户手机号/设备/IP 与全部反馈。`monitor-admin.guard.ts:27-40`。
10. **看板缓存串号**：缓存 key 不含 userId，但响应含「我的排名」，同班后访问者会看到第一个请求者的排名数据。`data.service.ts:44,145`。

## 七、建议处理（P1：一致性与数据最小化）

1. 统一角色判定口径：任务/班费/投票/抽签/考勤/活动按 `is_committee`，消息/成员管理按 `role_level`；建议全部收敛到 `role_level`，并用数据库约束保证 `is_committee = role_level != member`。
2. 前端按钮与后端对齐：任务发布、抽签按钮对普通成员隐藏（或后端放开，需产品决策）。
3. 班费对全体成员开放查看/导出（含金额、备注、票据链接），建议明确产品策略；若为敏感数据，至少对普通成员隐藏备注中的姓名。
4. 通知导出明文手机号+学号，建议脱敏或限定 owner。
5. `/uploads` 静态资源公开，资料库与票据 URL 泄露即可被未登录者下载；建议改为带签名/有效期的访问地址。
6. 成员「班长」等 role 文案与真实权限脱节：导入名单里的班长仍是普通成员，需在 UI 明示或导入时自动映射（需产品确认）。
7. 权限双轨导致的体验问题：`is_committee=true` 但 `role_level=member` 的异常数据会让班级页「班级管理」入口消失而首页发文入口出现；建议加数据修复脚本。
8. 创建配额按 `creator_id` 统计且不过滤已解散组织，转让群主后新群主配额被占用。`can-create-class.guard.ts:47-53`。
9. 密码重置允许 admin 重置其他 admin，建议限制为 owner 或仅允许重置 member。`classes.service.ts:829-837`。
10. 隐私开关目前只被成员列表与考勤消费，班费/通知/资料库/监控台均未应用；要么扩大生效范围，要么在设置页标注生效范围。
11. 登录态健壮性：refresh 不查 `refresh_tokens`、logout 为空实现，改密后旧 refresh 仍可用；前端 401 无统一跳登录。`auth.service.ts:351-368,422,428-431`。
12. 前端核心路由统一包 `AuthRoute`，避免未登录直达页面后才报错。

## 八、需产品拍板（P2）

1. 加入组织是否需要审批、是否校验人数上限、邀请码是否可轮换（当前：无审批、无上限、不可轮换，6 位数字码可枚举）。
2. 投票进行中是否允许查看实时票数（当前允许）。
3. 抽签是否允许任意班委作废他人记录（当前允许）。
4. 班费账目是否对普通成员完全公开（当前公开）。
5. 签到是否要求更强凭证（当前 normal/qr 无凭证，可代签）。
6. 普通成员能否发布通知（当前可以，若保留需在文案上区分「班委通知」与「成员消息」）。

## 九、核查结论

- 角色体系本身清晰：owner / admin / member 三层 + 班委标记，班级隔离由全局守卫兜底。
- **高风险集中在「不需要班级 ID 的接口」和「服务层漏写归属校验」两类**：资料库、档案、专注、错误日志、Excel 导入。
- 班级管理与成员管理的主干权限（改信息、踢人、设管理员、转让、解散）实现正确，且有服务层二次校验。
- 建议先修 P0 十项，再做 P1 的判定口径统一，最后按 P2 与产品确认默认策略。
