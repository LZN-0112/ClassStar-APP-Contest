### D-01【高危·已修复】名单耗尽后实名名单保护完全失效

- **影响模块**：加入班级（`POST /api/v1/classes/join`）
- **复现步骤**：
  1. C 班导入 3 条名单，系统生成 3 个占位账号（199****0001~199****0003）。
  2. 3 名名单内学生分别用名单学号认领占位账号加入，占位成员数降为 0。
  3. 使用名单外账号 199****5555 调用加入接口，body 为 `{"code":"938882","studentId":"0000000"}`（错误学号）→ **返回 201，`verifyStatus=UNVERIFIED`**。
  4. 换另一个名单外账号不传 `studentId` 直接加入 → **同样返回 201**。
- **预期结果**：班级一旦导入名单，应永久要求学号且必须命中名单；名单外人员拒绝加入。
- **实际结果**：占位账号被认领完后，系统判定为「未导入名单班级」，走无名单分支直接放行。
- **根因定位**：[classes.service.ts](../../back/src/modules/classes/classes.service.ts#L174-L180) 用「现存 `password_hash=''` 占位账号数量 > 0」动态推导 `hasPrebuiltRoster`，该值会随认领而变为 `false`；随后进入无名单分支直接创建 `UNVERIFIED` 成员（同文件约 L247-L270）。
- **影响范围**：任何拿到 6 位邀请码的人都能进入已导入名单的班级，实名核实机制形同虚设；可进一步读取成员列表、参与缴费/抽签、获取班级数据。
- **修复建议**：在 `classes` 表增加持久化标记（如 `roster_imported` / `roster_version`，或独立名单表），导入后永久为真；`joinClass` 以该标记判断，名单已导入时必须校验学号在名单内且未被占用；不要用占位账号数量推导名单状态。
- **回归验证建议**：新增用例「名单全部认领后，名单外账号加入应 400」「错误学号加入应 400」。
- **修复记录（2026-11-11）**：
  - `classes` 表新增 `roster_imported BOOLEAN NOT NULL DEFAULT FALSE`（迁移 `20261111160000_add_class_roster_imported`），并按「存在占位账号（`password_hash=''`）或成员在创建后 10 分钟内被自动置为已确认」回填存量班级。
  - `joinClass` 改为读取 `classEntity.roster_imported` 判断名单状态，不再以占位账号数量推导；手动导入与 Excel 导入成功后均将该标记置为 `true`。
  - 复测结果（A 班占位已全部认领、`roster_imported=1`）：错误学号 `0000000` 加入 → 400「您不在班级名单中，请联系班长核实学号」；不传学号 → 400「该班级已导入名单，加入时需填写学号」；两次请求均未生成成员记录。B 班（`roster_imported=0`）仍走无名单直接加入逻辑。

### D-02【高危·已修复】导入名单按学号/手机号匹配既有账号，直接绑定并置已确认

- **影响模块**：名单导入（`POST /api/v1/classes/:id/members/import`）
- **复现步骤**：
  1. 库中存在历史用户：手机号 138****8001、姓名张三、学号 2023001。
  2. 向 A 班导入名单条目 `{"phone":"138****8001","name":"张三","studentId":"2023001"}`。
  3. 系统按 `OR phone / student_id` 命中该历史用户，**不创建占位账号**，直接将其加入 A 班并置 `verify_status='CONFIRMED'`、`verified_at=now`。
  4. 真正的名单学生无法再以 2023001 认领（占位不存在），名单条目被该账号占用。
- **预期结果**：导入名单只建立名单/占位记录，不应直接绑定既有账号并标记已确认；身份应由本人认领或班委核对后确认。
- **实际结果**：既有账号被直接当作名单本人，自动 `CONFIRMED`。
